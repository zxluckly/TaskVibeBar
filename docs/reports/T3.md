## 主 Agent 预检修正：Git 查询自激循环

**现象**：真实仓库空闲时日志每 0.5–1s 出现一次 `Git 查询成功`，2 分钟 117 次。

**根因**：`git status` 默认会为刷新 stat 信息而获取可选锁并写回 `.git/index`；GitProvider 的 `.git` FileSystemWatcher 捕获 `index` 变化 → 500ms 防抖 → `RefreshSuggested` → 再次 `git status`，形成自激循环。

**修复**：在 `RunGitAsync` 的 `ProcessStartInfo.EnvironmentVariables` 中为子进程设置：

```text
GIT_OPTIONAL_LOCKS=0
GIT_TERMINAL_PROMPT=0
GIT_PAGER=cat
```

`GIT_OPTIONAL_LOCKS=0` 禁止 `git status` 写回 index/lock；未改 `.git`/工作区监听、500ms 防抖、worktree、错误降级等其余 T3 逻辑。

**验证**（独立验证程序，`GitProvider` + `ProviderScheduler`，等价 AppController 的查询/轮询链路）：

- 仓库 6 个已修改文件，首次查询及再次查询后 `.git/index` 的 **SHA-256 字节、文件长度、LastWriteTimeUtc 均完全一致**。
- 两次查询后等待 1.5s/1s，`RefreshSuggested` 触发次数均为 **0**。
- 空闲 **60s 内 Git 查询次数 = 2**，时间点 `1058ms`、`31117ms`（首次 + 30s 轮询），`watcherEvents=0`，查询间隔 ≥25s。
- 回归：工作区修改后 `RefreshSuggested` 仍在 **510ms** 触发；`git status` 结果正确；假 git 超时 **5018ms** 被杀、错误仍为 `git 命令超时`。

## 补充实现说明

- 规格要求 FileSystemWatcher 监听 `.git`，但 GIT-02 与“修改文件后 <2s”自测要求感知工作区普通文件修改/新增，而这类操作不会写 `.git`。因此 GitProvider 在 `.git` 元数据监听之外，额外监听仓库工作区（`IncludeSubdirectories=true`，过滤 `.git` 下的路径），两者共用 500ms 防抖。未改变 `IProvider`、模型或 AppController 事件契约。若主 Agent 只接受监听 `.git`，需同时下调 GIT-02 的 2s 验收口径。

## 已知问题

- 同时存在普通脏文件与冲突时，段格式为 `分支*脏!冲突↑N↓M`（例 `main*3!2`），单独冲突时与规格一致为 `main!2`；规格未定义两者并存时的文案。
- 有效仓库的详情面板总是显示 `领先：0 · 落后：0`；段在两者均为 0 时不追加箭头。规格“绝不显示 0”仅针对无仓库/错误态，此处为有效数据。
- `git.pollSeconds` 增加了 86400 上限：现有 `ProviderScheduler` 将 >1 天的间隔视为事件驱动（`TimeSpan.MaxValue` 语义），不设上限会导致成功后退化为不再轮询。规格只写了“默认 30、最小 10”，此上限为防御性措施。
- 工作区监听为满足 2s 刷新而增加的实现（见“补充实现说明”），大仓库/海量文件变动时可能触发监听缓冲区错误；已降级为 30s 轮询。
- 自激循环修复后，`git status` 不再顺带刷新 `.git/index` 的 stat 缓存；这不影响状态正确性，但 `git status` 可能略微多做 stat 检查（本机 11,000 文件仍为 64ms 量级）。
- 通用非 0 退出文案为 `git 命令失败：<stderr 首行>`；非仓库被单独映射为 `Unavailable`/`不是 Git 仓库`。
- 详情面板沿用 T2 的 `VibeBar` 总标题，Git 作为独立 `DetailSection`；T5 可统一视觉。
